## 1. What we are building (one paragraph)

A citizen-facing **explainable assistant for Swiss public transport**. A commuter asks
"Is my connection at Olten reliable? I have 4 minutes." The assistant answers with a
decision word (*safe / at risk / risky*) and an explanation made of **fuzzy linguistic
summaries** ("On about half of Monday mornings your train arrives too late for a 4-minute
transfer", truth 0.74, based on 38 trains), computed from opentransportdata.swiss
Ist-Daten. The explanation is the Computing-with-Words (CWW) core, not an add-on: the
decision and its explanation come from the same truth computation, so they are faithful
by construction. We then test whether an LLM (Apertus-8B) that phrases such answers stays
truthful, using a crisp checker and our fuzzy checker.

Course: Seminar Urban Computing, Human-IST, University of Fribourg (AS-2026).
Deadline: **6 Dec 2026** (code, paper, slides).

## 2. Research questions (frozen; details in docs/PROJECT.md and eval/hypotheses.yaml)

- **Main RQ:** Can fuzzy linguistic summaries be the explainable core of a citizen-facing
  assistant that answers questions about the reliability of Swiss public-transport trips?
- **SRQ1 "Is the answer about my trip?"** With Hudec's coverage and regional quality, which
  summaries still hold for a citizen's own line/station/time, and how often do network-wide
  summaries mask local reality?
- **SRQ2 "At risk for whom?"** How often does the crisp official view (SBB 3-minute rule)
  give a different verdict than a perception-aware view based on the passenger's margin?
- **SRQ3 "Can I trust the chatbot?"** Are LLM-written quantified claims faithful to the data,
  and where do a crisp checker and the fuzzy checker disagree?

Re-implementing Pincay, Portmann & Terán (2021) is a **baseline**, not a research question.

## 4. Hard rules (a PR that breaks one is rejected)

1. **Raw data is immutable.** Never write, rename or "fix" anything under `data/raw/`.
   Derived data goes to `data/interim/` or `data/processed/` via code in `src/`.
2. **No data, model weights or LLM outputs in git.** Only tiny synthetic fixtures in
   `tests/fixtures/` (< 200 KB each, generated by code you commit).
3. **Pre-registration is frozen.** Do not change `eval/hypotheses.yaml` thresholds or
   `config/*.yaml` values to make a result look better. A needed change = a decision
   proposal in `docs/decisions.md` (status `proposed`) + PR comment; the PM decides.
4. **One ticket per PR.** Stay inside the ticket's `touches:` paths. If you must touch
   other paths, say why in the PR.
5. **Tests are part of the ticket.** Every acceptance criterion maps to at least one test
   or a reproducible command. `make check` must be green. Tests must not need network,
   real data or a GPU unless marked `@pytest.mark.realdata` / `@pytest.mark.gpu`.
6. **Determinism.** Seeds from `config/study.yaml`. Same input → same output, byte-equal
   where feasible. Log library versions in generated reports.
7. **No invented facts.** Do not invent dataset fields, paper results, formulas or
   citations. If a formula comes from a paper, cite it in `docs/methods.md` with page /
   equation number. If you cannot verify something, write `TODO(verify)` and flag it in
   the PR description.
8. **Names.** Say "Swiss public-transport assistant", never "SBB assistant" (the data
   covers all operators; no official branding in the prototype).
9. **Frozen interfaces.** Function signatures in the module stubs, table schemas in
   `src/urban_computing/data/schemas.py`, the pydantic contract and `SummaryRecord` are
   guarded by `tests/test_interfaces.py`. Other agents code against them in parallel.
   Changing one needs a decision proposal and an update of that test in the same PR.
10. **Stay in your stub.** A stub raising `NotImplementedError("UC-xxx")` belongs to ticket
    UC-xxx. Do not implement another ticket's stub; mock it in your tests instead.
11. **Dependencies.** Only UC-001 commits `uv.lock`. Do not add packages; if you need one,
    say so in the PR (the PM adds it in a separate change).
12. **Pure core.** `src/urban_computing/fuzzy/` has no I/O and no pandas/duckdb imports;
   it works on NumPy arrays. Heavy LLM libraries are imported lazily inside `llm/`.

## 5. How to work a ticket

1. Pick a ticket with `status: todo` whose **hard** `depends_on` tickets are all `done`
   (`python3 scripts/tickets.py ready`). In automated runs the dispatcher picks for you.
2. **Soft dependencies** (`soft_depends_on`) are tickets whose code may not exist yet but
   whose interface does. Code against the stub signatures and build test data with
   `tests/factories.py`. Mock unimplemented functions with `monkeypatch`. When the soft
   dependency later merges, your tests must still pass unchanged.
3. Branch: `uc-XXX-short-slug`. Set the ticket `status: in-progress` in your first commit.
4. Implement. Write tests first for the acceptance criteria where possible.
5. Run `make check`. In automated runs without network use `UV_OFFLINE=1 make check`.
6. **Real data** (`realdata: true`): deliver the code, fixture-based tests and the exact
   command to run on real data. Do not wait for real data; Nikhil runs the commands in
   batches from `docs/REALDATA_RUNS.md`. The ticket is `done` when code + tests merge.
7. Update docs the ticket names (methods, data, decisions proposals).
8. Set `status: done` in the ticket file in the same PR. Fill the PR template.
   PR title `UC-XXX: <title>`; body contains `Closes #<issue>` (see `tickets/ISSUE_MAP.json`).
9. Commit messages start with `UC-XXX:`.

If blocked: set `status: blocked`, add a `## Blocker` section to the ticket explaining what
is missing, and stop. Do not work around a blocker by changing scope.

## 6. Definition of Done (task level, see docs/evaluation.md)

- [ ] Every acceptance criterion in the ticket is met and covered by a test or command
- [ ] `make check` green; no new ruff warnings
- [ ] Public functions have type hints and a docstring stating inputs, outputs, units
- [ ] Outputs land in the paths the ticket names, with the schema the ticket names
- [ ] Docs updated (`docs/methods.md`, `docs/data.md`, …) as the ticket requires
- [ ] No rule in §4 broken; deviations listed in the PR description

## 9. Automated dispatch (see docs/ORCHESTRATION.md)

`.github/workflows/dispatch.yml` starts Claude Code or Codex on ready tickets whenever
`main` changes. Labels: `agent:running` (in flight), `agent:claude` / `agent:codex`
(who), `agent:failed` (needs a human; the dispatcher will not retry it). A human merges
every PR.

## 8. Environment notes

- Python ≥ 3.11, dependencies via `uv` (pyproject.toml).
- Real data and LLM runs happen on the user's cloud VM / the UBELIX cluster
  (University of Bern). CI never downloads data.
- Ist-Daten daily files are large (hundreds of MB/day). Use DuckDB reading CSV directly
  and write Parquet; do not load a month into pandas.
